# v0.2 backlog — Playable World

v0.2 exists to correct the gap exposed by the first public Pages demo: WorldBoxSR has meaningful simulation depth, but still reads visually as a developer prototype.

## Release outcomes

- [ ] choose and implement the rendering stack that best accelerates 2D game presentation (keeping the simulation core isolated)
- [ ] replace flat debug tiles with a coherent original terrain/tile presentation
- [ ] add visible coastline/water/vegetation/biome detail
- [ ] replace human/grazer debug primitives with readable sprites and movement interpolation/animation
- [ ] show settlement growth with structures/buildings, labels/flags and territory boundaries
- [ ] replace the debug-first HUD with a compact game-first control/tool layout
- [ ] add immediate visual feedback for spawn, erase and lightning
- [ ] create a default scenario/preset that looks alive immediately
- [ ] verify the 5-second and 30-second product gates on the public Pages demo
- [ ] keep deterministic simulation/save-load/regression contracts green

## Mandatory gates

### 5-second gate
A first-time viewer, without documentation, can identify terrain, living units, settlement presence and god-game controls.

### 30-second gate
Within 30 seconds of opening the default demo (or using an obvious speed control), a legible world change/event occurs.

### Screenshot gate
Every visual/game-feel PR must preserve before/after evidence in the PR or linked issue.

### Product gate
Green tests are necessary but insufficient. The public Pages demo must be materially more game-like than v0.1.

## Priority constraints

Until these gates pass:

- no new non-correctness ecology research;
- no tuning compact grazer persistence/initializer hypotheses;
- no new invisible analysis subsystem unless it directly improves the playable UI;
- no infrastructure work unless it blocks rendering, verification or deployment;
- prefer existing assets/tools/libraries or AI-assisted asset production over hand-building low-level rendering infrastructure when the former delivers visible quality faster.

## Candidate workstreams

### Rendering foundation
Evaluate the smallest migration that gives us sprites, tilemaps, layers, particles/effects, camera support and fast iteration without moving authoritative simulation logic into the renderer. Phaser 4 or PixiJS are acceptable candidates; select based on the first concrete vertical-slice spike, not framework ideology.

### World art pass
Terrain tiles, coastlines, vegetation props, settlement structures, readable palette and depth cues. Assets must be original; do not copy WorldBox assets/branding.

### Living entities
Sprites, directional/idle/movement presentation, readable scale, simple interpolation and selection feedback for humans/grazers.

### Settlement legibility
Buildings/structures driven by existing settlement state, labels/flags, population cues and territory boundaries.

### God-game feedback
Compact toolbar, cursor/tool state, spawn/erase/lightning effects and short-lived particles/flash/shake where appropriate.

### Default demo
A fixed, reproducible scenario tuned for visual communication rather than research neutrality: enough population, speed and starting context that the page is immediately worth watching.

## Deferred to v0.3 — Living Ecology

The previous v0.2 ecology plan is preserved as later work: natural-fauna activation semantics, supported map/preset matrix, deterministic initializer promotion and ecology-specific observability. Existing Sprint evidence remains valid and must not be discarded.

## Explicit non-goals

- matching WorldBox feature breadth in v0.2;
- kingdoms/diplomacy/war;
- predators/multi-species food webs;
- universal fauna survival;
- final production-quality art pipeline.
