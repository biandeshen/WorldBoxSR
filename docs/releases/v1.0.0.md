# WorldBoxSR v1.0.0 — Stable Sandbox Identity

v1.0.0 is the point where WorldBoxSR freezes a dependable product contract around the sandbox that was built through v0.1–v0.9. It is **not** a breadth-mechanics release.

> **WorldBoxSR behaves like one dependable sandbox product: reproducible worlds, stable browser play, recoverable saves, understandable history, supported public surfaces, and coherent creation/intervention/civilization/ecology/story workflows.**

## Capability 1 — Portable Compatibility Contract

v1.0 makes the existing portable-state behavior an explicit supported contract instead of an implicit migration implementation.

### Engine snapshots

Current engine schema remains **snapshot v16**.

The frozen supported historical baseline is:

`[10, 11, 12, 13, 14, 15, 16]`

`worldFromSnapshot()` derives acceptance from the exported immutable `SUPPORTED_SNAPSHOT_VERSIONS` list.

An independently named compatibility matrix now proves every version separately:
- v10 — older pre-reproduction / pre-polity prototype shape;
- v11 — reproduction fields allowed, still pre-polity;
- v12 — polity state allowed, pre-relations;
- v13 — relations allowed, pre-warbands;
- v14 — warbands allowed, pre-v16 ruling-line fields;
- v15 — public pre-ruling-line schema used by v0.3.0, v0.4.0 and v0.7.0;
- v16 — current public schema used by v0.8.0 and v0.9.0.

For every supported version, migration must:
- leave the supplied snapshot unmodified;
- normalize to current v16;
- remain deterministically identical to a fresh restore of the normalized v16 state after the same 12-tick continuation.

Unsupported below-floor, non-supported and future engine versions reject explicitly.

### Ordinary local-world saves

The browser-local ordinary-world envelope remains **format v1** and embeds the normal engine snapshot rather than creating a second world format.

Envelope v1 is verified against every supported historical engine snapshot. Future envelope versions and unsupported embedded engine versions reject explicitly instead of replacing the current world.

### Scenario Recipe

Scenario Recipe **v1** remains the separate canonical Scenario identity. Future unsupported Recipe versions reject explicitly; v1.0 does not invent Scenario migration semantics.

## Capability 2 — Certified Runtime & Recovery Envelope

v1.0 states exactly which runtime surfaces the project actually certifies through production-built evidence.

Canonical contract: `docs/SUPPORT.md`.

### Certified

- **Chrome/Chromium-class desktop Phaser · 1440×900**;
- **Chrome/Chromium-class coarse-touch Phaser · 430×820**;
- existing **Legacy Canvas** as an explicit **ordinary-world compatibility fallback**.

The production Phaser desktop gate requires the real Pages/Vite base path, `Phaser 4 · authoritative simulation · showcase ready`, no renderer failure, and real interaction evidence.

The certified touch contract is:
- tap — selected God Power / Scenario placement;
- hold — inspect without another command;
- drag — pan;
- two-finger pinch — zoom while preserving focus and world authority;
- after both pinch fingers release, a fresh one-finger action works normally.

### Explicit limitations

- Scenario remains **Phaser-only**; Legacy fallback is not feature-equivalent and must disclose any Scenario consequence;
- Firefox/Gecko and Safari/WebKit remain **uncertified / best effort** until real gates exist;
- 430×820 is the certified touch QA surface, not a guarantee for every mobile browser/device/screen;
- there is no cloud save or cross-device sync claim.

### Structural performance/build contract

The public 24×24 showcase is the initial v1.0 product performance envelope.

Release build checks require:
- exactly one dedicated `phaser-vendor-*.js` chunk;
- exactly one `phaser_main-*.js` app chunk;
- `phaser_main` ≤ **300,000 bytes** minified;
- vendor chunk larger than the application chunk.

The 64×64 1k/10k Node benchmark remains diagnostic. It is not promoted to an FPS/tick SLA because no runner-independent non-flaky threshold has been calibrated.

## Proven integration correction

The final cross-system gate discovered one real public-alpha persistence defect:

**`Save now` remained disabled until the first 30-second autosave.**

The persistence UI rendered while the initial showcase was still booting and did not refresh again when warmup actually completed. That contradicted the v0.9 promise that a first checkpoint may be created by **Save now or the 30-second autosave**.

v1.0 fixes only that readiness seam: the persistence runtime now observes the initial boot→ready presentation boundary and immediately re-renders Session availability when the world is ready.

This does **not** change:
- local save envelope format;
- engine snapshot schema;
- autosave interval;
- restore authority;
- Scenario identity/suppression rules;
- simulation behavior.
